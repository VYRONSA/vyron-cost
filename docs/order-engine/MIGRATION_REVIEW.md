# Order Engine migrations — review

Four migrations, none applied to production. They were applied, re-applied and
exercised only on a disposable local Postgres
(`npm run test:order-engine-migration-pg`, 107 checks).

| # | File | What it adds |
|---|---|---|
| 1 | `20260922120000_vyron_order_intake.sql` | `vyron_order_source_messages`, `vyron_order_intakes`, `vyron_order_intake_lines`, `vyron_order_intake_events` (append-only) |
| 2 | `20260922130000_vyron_order_intake_hardening.sql` | composite tenant keys, approved mappings (revoke-only), customer order policies, source facts |
| 3 | `20260923120000_vyron_order_engine_food_sock.sql` | order context, frozen source snapshots (trigger), `external_id` / `b2c_account` match rules, `NEEDS_EXTRACTION`, `vyron_order_engine_settings` |
| 4 | `20260923140000_vyron_order_engine_channels.sql` | ordering decisions (D1–D12), `vyron_order_channel_settings`, `vyron_order_mailboxes`, `vyron_order_document_extractions`, `QUARANTINED` |

## 1. Forward migration

All four are forward-only and additive. Nothing drops a table, a column or a
row. The only constraints dropped are ones the same migration immediately
recreates with a wider allowed set (match rules, message statuses), so an
existing row can never become invalid.

Re-running any migration is a no-op: every object uses `if not exists`, every
constraint is dropped-then-added, and every trigger and function is
`create or replace`. Proved by applying each twice.

## 2. Constraints, indexes, tenancy

- Every table carries `company_id`; every unique index is per company, except
  `vyron_order_mailboxes.receiving_address`, which is deliberately **global** —
  the address decides which tenant an inbound message belongs to, so two
  companies must never claim the same one.
- Child rows are tied to their parent *and* its company through composite
  foreign keys `(intake_id, company_id)` / `(source_message_id, company_id)`,
  so a row cannot be attached across tenants even with a forged id.
- Business decisions are nullable with a check constraint on the allowed
  values. NULL means "not decided" and is never a rule.
- Indexes added for the real query paths: inbox by company and date, duplicate
  PO, duplicate external reference, context, mailbox by company and status,
  extraction attempts by company and status. Proved with `EXPLAIN` over 50 000
  synthetic rows (no sequential scans on the inbox paths).

## 3. RLS, grants and the service-role boundary

Every table: `enable row level security`, no policies, and
`revoke all … from anon, authenticated`. Only the service role (server code)
can read or write, exactly as the existing Order Engine tables. Helper
functions are revoked from `public`, `anon` and `authenticated` as well.

This matters because of the known open issue that the anon key can read many
older business tables ([memory: Supabase RLS is open to anon]). None of these
tables widen that surface.

## 4. Compatibility with the existing schema

- Nothing alters a Sales Order, invoice, stock, BOM or Xero table.
- `vyron_order_intakes.sales_order_id` is the only link into Sales Orders and is
  unique, so one intake maps to at most one sales order.
- No foreign key to `vyron_cost_companies`: not every live tenant has a row
  there (documented in migration 1), so a foreign key would break those
  tenants.
- The source-snapshot trigger fires only on `update` of the Order Engine's own
  tables and leaves every other write path untouched.

## 5. Rollback

Each migration's header lists its reverse steps (drop the new tables, drop the
added columns, restore the previous check constraints). No destructive rollback
migration has been written, and none should be created merely for testing:
dropping these tables discards received orders and their audit trail.

If a rollback is ever needed in production it must be a human-approved,
evidence-backed operation under the Family P safety process, taken after an
export of the affected tables.

## 6. Requires human approval before production

1. Applying all four migrations to the production database (a DDL change).
2. Confirming that the production `vyron_order_intakes.sales_order_id` unique
   index does not collide with any existing sales order id (it will not: the id
   is generated by the Order Engine, but this must be checked on the day).
3. Deciding whether `vyron_order_mailboxes` should hold a real receiving
   address before a provider connector exists (recommended: no — keep mailboxes
   `DISABLED` until the connector is live).
4. Confirming the tenant settings each company should start with; the engine's
   defaults deliberately decide nothing.
